# EasyCRM — Codex Session 1: Application Foundation, CRM UI & AI Model Settings

## Objective

Build the initial working version of **EasyCRM**, an AI-powered lead qualification and CRM platform.

The repository contains README.md, BRD.md, SRS.md, ARCHITECTURE.md, API_SPEC.md, and an attached UI/UX reference image.

**First, read all attached documentation and inspect the repository.** Treat the documents as the source of truth for the product architecture, functional requirements, and scope. Use the attached image as the primary visual reference.

Implement Session 1 as a working full-stack foundation, not static mockups.

## 1. Technology stack

- Frontend: React, TypeScript, Vite, Tailwind CSS
- Backend: Python, FastAPI, SQLAlchemy, Alembic
- Database: PostgreSQL
- AI providers: Google Gemini and NVIDIA NIM
- Async infrastructure: Redis/Celery only where immediately necessary
- Package services with Docker Compose for local development
- Provide clear Ubuntu development commands

Keep the architecture modular, maintainable, and suitable for future AI qualification, RAG, webhooks, and WhatsApp integrations.

Do not introduce unnecessary frameworks or microservices.

## 6. AI Provider Integration — Important

I have API credentials for:

1. Google Gemini models, including free-tier models where available
2. NVIDIA NIM API, including NVIDIA Nemotron 3 Ultra where available through my account

Implement a provider-agnostic AI service architecture.

Use environment variables for credentials:

```env
GEMINI_API_KEY=
NVIDIA_API_KEY=
```

Configure NVIDIA through its OpenAI-compatible API interface where supported.

Do not assume a fixed NVIDIA model ID. Confirm the exact supported model ID from provider configuration or documentation.

Create separate provider adapters:

- GeminiProvider
- NvidiaProvider

Both adapters must support a common interface for basic text generation, connectivity checks, error handling, and normalized responses.

Do not hardcode model selection into application business logic.

### AI Settings page

Build a working Settings → AI Models interface.

It must support:

- Provider selection: Gemini or NVIDIA
- Model selection from a configurable model catalogue
- Workspace default model selection
- Display whether the provider has server-side credentials configured
- Test Connection button
- Save Model Preferences button
- Persist preferences in PostgreSQL
- Show current active model
- Allow changing the active model without restarting the application

The model catalogue must support updating available model identifiers through backend configuration and/or model discovery where supported.

Never expose API keys to the frontend.

Never return credentials through settings APIs.

API credentials remain server-side in `.env`.

Changing the model from Settings should determine which provider and model future AI qualification requests use.

Implement a simple **AI Playground** where the authenticated user can send a test prompt through the selected model and view its actual response.

Include:

- Loading state
- Provider/model identification
- API errors
- Missing-key errors
- Timeout handling
- Basic token usage display when available

Do not fake successful API responses.

Do not implement autonomous agent workflows or production lead qualification in Session 1.
